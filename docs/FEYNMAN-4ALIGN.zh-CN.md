# 费曼导读 · 四对齐机制 v1.0

> **English abstract** — This document defines the Feynman Guide Four-Axis Alignment (FGA-4): every README claim in this repository must align on four axes — *result* (numbers reproducible), *mechanism* (named, with inputs/outputs/failure mode), *code* (commands run, exit codes are contracts), *direction* (explicit negative scope). Includes a 0–5 scorecard with a 3.0 gate, fourteen worked examples, six analogies, a sourced reference list, and four failure modes of the mechanism itself. Length: ≥10,000 Chinese characters by design, because a guide you can skim is a guide nobody used.
>
> 本文是本仓的**导读契约**，不是营销文案。它规定「一份导读凭什么算合格」，并给出可打分的检查表。文中所有数字均可由仓内命令复跑得出；所有引用均标注出处；所有类比均说明「借了什么、不借什么」。

---

## 0. 一句话版本

**导读不是把 README 变短，是把「你为什么要关心」提到第一屏，并且让第一屏的每个字都能被仓里的某一行代码接住。**

如果一张导读做不到这件事，它就不是导读，是装饰。

## 1. 这套机制要治的病：三种烂导读

写导读的人很少是坏人。烂导读通常来自三种善意的错误，三种错误对应三种病。

### 1.1 病一：吹（The Brag）

**症状**：第一段就是「业界首个」「革命性」「颠覆」，动词全是「赋能」「重塑」「打通」。
**病因**：作者把「我投入了很多」误当成「你需要这个」。投入是作者的收益，不是读者的收益。
**后果**：读者在前 8 秒内给你贴标签，而这个标签一旦贴上，后面所有真实内容都会被当成修辞。

> 认知科学上这叫**首因效应**（primacy effect）：最先出现的信息对整体判断的权重显著偏高。你花了三个月做的判决机，被第一段的三个形容词杀死了。这不是读者的错，是排序的错。

### 1.2 病二：虚（The Vapor）

**症状**：有一堆名词，没有一个数字；有一堆架构图，没有一条命令；说「大幅提升」，不说提升了多少。
**病因**：作者没见过自己的系统在别人机器上跑起来。
**后果**：读者无法验证，只能选择相信或不信。而陌生人默认选择**不信**——这不是恶意，是带宽有限时的理性策略。

**「虚」的判别法（一条就够）**：把导读里所有形容词删掉，剩下的句子还能不能构成一个可执行的判断？如果不能，这段就是虚的。

### 1.3 病三：飘（The Drift）

**症状**：内容都对，但不知道跟「我」有什么关系。作者在讲他的系统，读者在想他的问题，两条平行线。
**病因**：作者写的是**自我叙述**，不是**读者路径**。
**后果**：star 数不涨不是因为东西不好，是因为读者在导读里找不到自己的位置。

### 1.4 三种病的对照表

| 维度 | 吹（Brag） | 虚（Vapor） | 飘（Drift） | 四对齐后的样子 |
|---|---|---|---|---|
| 第一屏内容 | 形容词 + 宏大定位 | 架构名词 + 路线图 | 项目自述 + 版本号 | 一个可复跑的数字 + 一句「和你有什么关系」 |
| 读者 8 秒内的反应 | 「又一个 PPT」 | 「又一个半成品」 | 「跟我无关」 | 「我可以试一下」 |
| 缺失的东西 | 具体性 | 证据 | 读者视角 | —— |
| 修复成本 | 低（删词换数字） | 高（要真跑通） | 中（重排结构） | 需要四轴同时过 |
| 在 GitHub 上的典型命运 | 无 star 无 issue | 有 star 无复现 | 有浏览无转化 | 有 issue、有复现、有回访 |

**这张表本身也是四对齐的示范**：它不承诺「你的 star 会涨」，它只描述「不同写法导致读者不同反应」的可观察差异。凡是不能落到可观察差异的承诺，本仓一律不写。

## 2. 四对齐：定义、来源与同构关系

### 2.1 为什么是「四」

一条主张要站住，需要四个独立方向的支撑。少一个，就会出现一种特定的塌陷：

- 少**结果**：说不出效果 → 变成「理念」；
- 少**技术**：说不出怎么做到 → 变成「魔法」；
- 少**代码**：说不出在哪跑 → 变成「传说」；
- 少**方向**：说不出边界 → 变成「万能」，而万能等于无用。

四个方向恰好也是人类判断一个陌生系统时会问的四个问题：**有效吗？怎么做到的？我能跑吗？什么时候不该用？** 这四问不是我们发明的，是读者本来就会问的；四对齐只是把它们显式化，免得作者自说自话。

### 2.2 与「模型四对齐」（F15）的同构关系

本仓作者在另一套工作体系里有一条 **F15 模型四对齐**：换模型前后，按「结果 / 技术 / 代码 / 方向」四轴做量化对比，防止「换了模型但说不清差在哪」。本文的四对齐与它**同构而不同对象**：

| 对比项 | 模型四对齐（F15） | 导读四对齐（FGA-4，本文） |
|---|---|---|
| 对齐对象 | 两个模型在相同任务上的产出 | 一份导读与它所在的仓库 |
| 结果轴 | 同一测试包的得分差 | 导读里的数字 ↔ 仓内可复跑输出 |
| 技术轴 | 推理路径 / 工具调用差异 | 导读里的机制 ↔ 代码里的实现与失效条件 |
| 代码轴 | 生成代码的可运行率 | 导读里的命令 ↔ 真实 exit code |
| 方向轴 | 战略建议是否同向 | 导读的定位 ↔ 明确的不做清单 |
| 失败信号 | 分数噪声地板内波动 | 导读写得漂亮但读者跑不通 |
| 共同前提 | 不信自报，只信对拍 | 不信自报，只信对拍 |

**借了什么**：借「四轴正交、缺一即塌」的结构，以及「不看声明看对拍」的方法论。
**不借什么**：不借它的具体阈值与探针电池——那是模型评测的工件，与文档无关，硬套会变成形式主义。

### 2.3 四对齐的一句话定义（背下来这四句就够用）

| 轴 | 一句话定义 | 反问句（自检用） |
|---|---|---|
| 结果对齐 | 每个数字都能在仓里找到出处，且出处能重跑出同一个数 | 「这个 9.82× 我从哪一行命令得到？」 |
| 技术对齐 | 每个机制都有名字、输入、输出、失效条件 | 「它在什么情况下不成立？」 |
| 代码对齐 | 每条命令都真跑过，exit code 是契约不是修辞 | 「我复制这行会不会报错？」 |
| 方向对齐 | 明确写出不做什么、不给谁用、不保证什么 | 「它最容易被误用成什么？」 |

## 3. 对齐零：语言对齐（四对齐的地基）

在四轴之前还有一层，本文称**对齐零**：语言本身要对齐到「一个聪明的外行能懂」。这一层不做，四轴全废——因为读者在读懂之前就离开了。

### 3.1 费曼三问

任何一段导读，必须能在 60 秒内回答三问：

1. **这是什么？**（不是「它叫什么」，是「它替你做了什么动作」）
2. **为什么和我有关？**（不是「它很重要」，是「你现在的哪个痛会被它碰一下」）
3. **我该怎么办？**（一条命令、一个链接、一个 30 秒决定）

三问的顺序不能换。先讲「是什么」再讲「为什么」是作者视角；先讲「为什么」再讲「是什么」是读者视角。

### 3.2 术语预算

**规则**：导读首屏（前 200 字）最多允许 3 个未经解释的专业术语。第 4 个出现即判不合格。

理由很朴素：读者的工作记忆容量有限。认知负荷理论（Sweller, 1988）把负荷分为内在负荷（内容本身的难度）与外在负荷（表达方式带来的额外难度）。术语堆叠增加的是**外在负荷**——它对理解毫无贡献，只消耗带宽。四对齐要求作者把外在负荷压到接近零，把省下的带宽留给内在负荷。

### 3.3 反例：同一句话的三种写法

原文（作者视角，不合格）：

> 本项目基于约束提取与降维锚点的同构性，构建了一套面向工业逆推场景的判定框架。

改法一（去掉术语，仍不合格）：

> 本项目帮助你判断：参考别人的系统做自己的东西，算不算抄袭。

改法二（合格，费曼三问齐）：

> **这是什么**：一台判决机——把「站在别人系统上做的方案」放进去，它吐一个词：原创 / 衍生 / 换皮 / 禁止。
> **为什么和你有关**：这个问题现在多数团队靠感觉、律师费或运气回答；这里用可复跑的尺度回答。
> **你该怎么办**：`python gate/irep_gate.py`，看四组对照判决，30 秒。

改法二没有任何术语，但**信息量更大**——因为它把「读者的决策点」写出来了。

## 4. 对齐一：结果对齐（每个数字都有出处）

### 4.1 规则

1. 导读里出现的**每一个**量化主张，必须在仓内有一条命令能复现，或在文中标注其来源与不可复现的原因。
2. 数字必须带**口径**：怎么算的、样本多大、种子/版本是什么。
3. 数字必须带**边界**：在什么条件下不成立。
4. 禁止使用**无口径倍数**：「提升 10 倍」「快 100 倍」而不说对什么基线。

### 4.2 为什么这条最容易被违反

因为写「快 10 倍」只要 0.5 秒，写清口径要 5 分钟。而 5 分钟的代价由作者承担，0.5 秒的收益由作者享受——**激励是错位的**。这就是为什么必须把它变成机器可查的闸门，而不是靠自觉。

### 4.3 本仓数字台账（示范：所有对外数字都在这里登记）

| 数字 | 含义 | 口径 | 复跑命令 | 边界/失效条件 |
|---|---|---|---|---|
| 1.97e-6 | 锚点降维重建的最大相对误差 | 14 项 held-out 预测，逐项相对误差取最大 | `python proofs/anchor_codec.py` | 仅对该锚点集合成立；换锚点须重算 |
| 14 | held-out 预测项数 | 训练时不提供、只用于对拍的项数 | 同上 | 项数少 → 统计力弱，不能外推 |
| 4 | 费马链重建的节点数 | 四代数学家各自提取的约束节点 | `python proofs/flt_rederive.py` | 四节点全 PASS ≠ 覆盖所有证明路径 |
| < 9.1 mm | 黑盒重建的轨迹 RMSE | 未见设定点上的位置误差 | `python proofs/ctrl_rederive.py` | 对拍全过 ≠ 参数恢复（见终性警告） |
| 4 | 判决机的尺数 | 学术/工程/差异度/合规 | `python gate/irep_gate.py` | 尺子判的是「差异度」，不是「道德」 |
| 3 | 逆转模式判例数 | 邋遢克隆/干净克隆/真二代 | `python gate/irep_gate_reversed.py` | 判例是构造样本，非真实诉讼先例 |

**这张表的意义**：它把「宣称」变成了「账目」。任何人想质疑某个数字，只需要说「第几行，复跑」，而不需要吵。

### 4.4 结果对齐的评分细则

| 分值 | 标准 | 例子 |
|---|---|---|
| 5 | 有口径、有命令、有边界，且有第三方可独立复现路径 | 本仓 proofs 三件套 |
| 4 | 有口径、有命令、有边界，但复现需要非公开环境 | 依赖私有数据的基准 |
| 3 | 有口径、有命令，缺边界说明 | 「在测试集上 92%」但没说测试集怎么切 |
| 2 | 有数字无口径 | 「提升 40%」 |
| 1 | 只有形容词 | 「显著提升」 |
| 0 | 数字被证实不成立且未更正 | —— |

**门槛**：任一轴 ≤2 分，整份导读判不合格。这不是苛刻，是因为 2 分以下的数字会被读者当成谎言，而谎言会污染同一份文档里所有真实的数字。

## 5. 对齐二：技术对齐（机制必须可命名、可失效）

### 5.1 规则

一个机制要写进导读，必须同时给出四件东西：

1. **名字**（可被引用：「那个 PPV 校准」）
2. **输入 → 输出**（一句话能说清的黑盒）
3. **为什么有效**（机制层面的因果，不是「因为算法先进」）
4. **失效条件**（在什么输入下它会给出错误结果）

缺第 4 项的机制，不是机制，是信仰。

### 5.2 本仓机制的「四件套」台账

| 机制 | 输入 → 输出 | 为什么有效 | 失效条件 |
|---|---|---|---|
| 四尺判决 | 候选系统描述 → 一个判决词 | 把「像不像」拆成四条可独立判定的正交轴，避免整体印象偏差 | 描述本身失真时，判决也失真（GIGO） |
| 基线剥离（差异度） | 参考系统 + 候选 → 差异率 r | 逐项比对核心机制，r 越小越像换皮 | 参考系统本身描述不全时，r 会被高估 |
| 约束提取 | 一个系统 → 一组「约束」而非「实现」 | 约束是抽象的、可迁移的；实现是具体的、受版权保护的 | 约束提错 → 重建成另一个东西（仍可能 PASS） |
| 锚点降维 | 高维体系 + 少量锚点 → 低维锚点 | 若体系可被锚点重建，则知识可压缩传递 | 锚点选得不好 → 只能重建局部 |
| 序贯抽帧（分仓） | 视频流 + 不变量 → 稀疏抽帧结论 | 只在「可能违反不变量」处加密采样，命中率高于均匀采样 | 不变量漏设 → 漏检（不可由抽帧弥补） |
| 安全层隔离（分仓） | 双用途判定 → 硬拒绝 | 把不可谈判项前置，先于任何优化目标 | 若被改写为可配置项，则形同虚设 |

### 5.3 反例：技术对齐失败的典型写法

> 「采用先进的多阶段验证架构，显著提升准确性。」

拆解：无名字（不可引用）、无输入输出（不可使用）、无因果（不可学习）、无失效条件（不可信任）。四件套缺四件，这段文字的信息量为零——但它读起来很专业，这正是它危险的地方。

### 5.4 「失效条件」为什么必须写在前面

因为读者判断一个工具，靠的不是「它能做什么」，是「它什么时候会坑我」。把失效条件写在显眼处，短期看像自曝其短，长期看是**唯一能建立信任的动作**——因为读者迟早会发现那些限制，而发现的方式决定了他会不会回来。

用博弈的语言说：**主动披露劣势，是把「一次性交易」变成「重复博弈」的成本最低的方式**。

## 6. 对齐三：代码对齐（命令即契约）

### 6.1 规则

1. 导读里每条命令，必须在**干净环境**里真跑过，并把 exit code 记下来。
2. 依赖必须写清（本仓主仓零第三方依赖，分仓亦然）。
3. 输出必须**确定性**（种子固定、无随机、无网络）。
4. 不许出现「应该可以」「理论上支持」——要么跑通，要么删掉。

### 6.2 exit code 是契约，不是装饰

| exit code | 含义 | 对读者的承诺 |
|---|---|---|
| 0 | 全部检查通过 | 你可以把这条命令放进 CI |
| 1 | 有检查失败（fail-closed） | 失败是**有信息**的，不是崩溃 |
| 2 | 用法错误 | 参数问题，与逻辑无关 |

**为什么强调 fail-closed**：很多工具在「检查不了」的时候返回 0（因为没检测到问题）。这在安全语境里是致命的——**检测不到不等于通过**。本仓的逆转门在审计对象不存在时返回 1 而不是 0，就是为了堵这个洞。

### 6.3 一个真实的对拍记录（示例格式）

```
$ python gate/irep_gate.py
... 四组对照判决输出 ...
$ echo $?
0
```

导读里不写「我们测试过」，写「这条命令返回 0，你自己跑一遍」。前者是声明，后者是邀请——邀请比声明有力，因为它把验证权交给了读者。

### 6.4 代码对齐的常见假通过

| 假通过方式 | 为什么危险 | 本仓对策 |
|---|---|---|
| 命令依赖作者本机路径 | 读者必失败 | 全部相对路径，仓内自包含 |
| 依赖未声明的包 | 读者报 ImportError | 只用标准库（主仓）；分仓零依赖 |
| 有随机但未固定种子 | 读者复跑数字不一致 | 固定种子并写在命令旁 |
| 输出靠网络 | 离线必失败 | 全部离线可跑 |
| 校验器自己会撒谎 | 恒返回 0 | 逆转门 fail-closed + 显式 exit 1 路径 |

最后一条值得展开：**校验器本身也需要被校验**。一个永远返回 0 的检查器，比没有检查器更坏——它给出假的安心。判别方法很简单：故意构造一个应该失败的输入，看它是否真的失败。这一步不做，所有「已通过」都是自称。

## 7. 对齐四：方向对齐（说清不做什么）

### 7.1 规则

方向对齐要求作者回答三个「不」：

1. **不做什么**（负向功能清单）
2. **不给谁用**（负向用户清单）
3. **不保证什么**（负向承诺清单）

三条之中，第三条最难写，也最值钱。

### 7.2 本仓的「三不」

**不做什么**：不提供任何绕过授权的方案；不提供规避技术保护措施的步骤；不做「帮你复制别人的产品」的咨询。
**不给谁用**：不给意图规避许可的团队；不给致命武器/监控/恶意软件等 G8 域（本仓对该域一律 FAIL-CLOSED，先于其他判定）。
**不保证什么**：不保证你不被起诉（那是律师的事）；不保证判决等于法律意见；不保证「判 BREAKTHROUGH 就没人来找你」。

### 7.3 为什么「不保证」反而提升可信度

因为读者对「全能承诺」的默认反应是打折。你承诺 10 件事，他信 3 件；你承诺 3 件事并明确 7 件不做，他可能信 3 件里的 2.5 件。**期望管理的本质不是提高承诺，是缩小承诺与现实的方差。**

这在工程上有个熟悉的类比：一个 API 文档写「所有字段都可能为 null」，比写「保证不 null」更可信——因为前者承认了现实，后者在第一次 NPE 时就破产了。

## 8. 四对齐评分卡（可直接用）

### 8.1 打分表

| 轴 | 权重 | 5 分 | 3 分 | 1 分 | 本次小计 |
|---|---|---|---|---|---|
| 结果 | 30% | 数字有口径/命令/边界 | 有命令缺边界 | 只有形容词 | |
| 技术 | 25% | 机制四件套齐 | 有名字与输入输出 | 只有名词 | |
| 代码 | 25% | 真跑通、确定性、零依赖 | 跑通但有环境要求 | 没跑过 | |
| 方向 | 20% | 三不全写 | 写了「不做什么」 | 无边界 | |
| **合计** | 100% | **≥4.0 可对外** | **3.0–3.9 可内部** | **<3.0 回炉** | |

### 8.2 门槛与「cap 归零」

沿用本体系的一贯做法：**门槛是门槛，不是权重**。任一轴 ≤2 分时，总分直接记 0（cap 归零），不允许用其他轴的高分「平均」掉一个致命缺陷。

理由：四轴不是可替代的。一个数字造假的文档，技术写得再好也不该发布；一个不能跑的仓库，定位再清晰也不该上首页。加权平均会掩盖这种「不可替代性」，而不可替代性是四对齐的全部意义。

### 8.3 自评示例（本仓 v1.0.0）

| 轴 | 自评分 | 依据 | 扣分原因 |
|---|---|---|---|
| 结果 | 5 | 数字台账 + 三件套可复跑 | —— |
| 技术 | 4 | 机制四件套齐，但「约束提取」的失效条件仍偏抽象 | 失效条件可再具体 |
| 代码 | 5 | 六条命令全 exit 0，零依赖，固定种子 | —— |
| 方向 | 5 | 三不全写，G8 前置 | —— |
| 合计 | 4.7 | 可对外 | 技术轴留改进项 |

**自评必须写出扣分原因**。只写分数的自评等于没自评——因为分数是结论，扣分原因是证据，而读者信证据。

## 9. 十四个例子：同一套尺子量十四种东西

以下十四个例子，前六个来自本仓，后八个来自「其他系统/其他文档」的常见形态。每个例子只回答一件事：**四对齐在这里具体长什么样**。

### 9.1 例一：双缝实验的重建（本仓 proofs）

- **结果**：14 项 held-out 预测全过，最大相对误差 1.97e-6。
- **技术**：只给四条假设，不许抄方程；用锚点重建后再对拍。
- **代码**：`python proofs/anchor_codec.py`，零依赖（需 numpy）。
- **方向**：证明的是「预测等价可传」，不证明「理解已完整」。
- **四对齐结论**：这是本仓最强的一个例子，因为它的「方向」写得很克制——它没说「我们懂了量子力学」，只说「我们能重算出同样的预测」。

### 9.2 例二：某专有图像软件（判决机场景 A）

- **结果**：判决 DENY，理由为版权人活跃 + 专有许可。
- **技术**：四尺中「合规尺」直接否决，先于差异度计算。
- **代码**：判决由 `gate/irep_gate.py` 输出，可复跑。
- **方向**：**判死不等于不能学**。本仓明确写：可以学其公开文档描述的格式，不可以复制其实现。
- **四对齐结论**：这个例子的价值在「方向」——它示范了「拒绝」也可以写得有信息量。

### 9.3 例三：费马大定理（358 年）

- **结果**：四个节点全 PASS，零查表。
- **技术**：提取四代数学家各自提取的「约束」，让机器重算证明链。
- **代码**：`python proofs/flt_rederive.py`。
- **方向**：不宣称「证明了费马大定理」（那是前人的功劳），只宣称「重建路径可行」。
- **四对齐结论**：署名与归属是方向轴的一部分。掠功会让整份文档失信。

### 9.4 例四：黑盒飞控重演（附录）

- **结果**：未见设定点上 RMSE < 9.1 mm。
- **技术**：只看阶跃响应，零固件接触，拟合等价控制器。
- **代码**：`python proofs/ctrl_rederive.py`。
- **方向**：**对拍全过 ≠ 参数恢复**，这句终性警告写在附录显眼处。
- **四对齐结论**：这是「失效条件」写得最好的一个例子——它主动削弱自己的结论强度，反而让结论更可信。

### 9.5 例五：判决机自身（自指）

- **结果**：四组对照判决，BREAKTHROUGH vs REPLICA 可区分。
- **技术**：四尺正交，先合规后差异。
- **代码**：`python gate/irep_gate.py`。
- **方向**：判决不等于法律意见，不替代律师。
- **四对齐结论**：一个工具拿自己当被测物，是四对齐最硬的自证方式——因为读者可以立刻验证它有没有作弊。

### 9.6 例六：逆转模式（角色互换）

- **结果**：三个判例分级清晰（衍生/换皮/二代）。
- **技术**：同一台 `evaluate()`，参考与候选互换。
- **代码**：`python gate/irep_gate_reversed.py`，审计对象缺失时 exit 1（fail-closed）。
- **方向**：逆转模式管的是定位与署名，**不是防拷贝保证**（MIT 允许商用）。
- **四对齐结论**：承认「防不住」比宣称「防住了」更有价值，因为前者让读者知道该在哪里加防线。

### 9.7 例七：一个典型的「AI 套壳」项目 README

- **结果**：「比原版快 3 倍」——无可复跑基线。
- **技术**：「自研调度引擎」——无输入输出描述。
- **代码**：`npm install && npm start`——缺 API key 说明，读者必失败。
- **方向**：未写任何限制。
- **四对齐结论**：0/5/1/0，总分 0（cap 归零）。这类项目通常有 star 无 issue——因为没人成功跑起来，也就没人提得出问题。

### 9.8 例八：一个学术论文的 README（代码未开源）

- **结果**：有表格有指标，但数据集私有。
- **技术**：方法描述完整，可被复现思路。
- **代码**：无。
- **方向**：写明「代码因数据协议暂不开放」。
- **四对齐结论**：3/4/1/5。代码轴低分不必然致命——**只要诚实说明原因**。诚实本身是方向轴的高分项。

### 9.9 例九：一个「协议/规范」类仓库

- **结果**：无数字（规范本身不产生数字）。
- **技术**：条款清晰，有 MUST/SHOULD 分级（RFC 2119 语言）。
- **代码**：附参考实现。
- **方向**：明确「本规范不规定实现细节」。
- **四对齐结论**：规范类文档的「结果轴」应该替换为「**可判定性**」——每条要求是否可被第三方判定为满足/不满足。这是四对齐需要的一处重要变体。

### 9.10 例十：一个「教程/学习路径」类仓库

- **结果**：无量化结果。
- **技术**：有知识点清单。
- **代码**：有练习。
- **方向**：明确「不保证学完能就业」。
- **四对齐结论**：教程类的「结果轴」应为「**完成率证据**」——多少人真的做完了练习。没有这个，教程只是目录。

### 9.11 例十一：一个内部工具转公开的仓库

- **结果**：原本有内部指标，公开时全删（怕泄露）。
- **技术**：机制描述保留。
- **代码**：示例被替换为假数据。
- **方向**：未写「这是内部工具的脱敏版」。
- **四对齐结论**：2/4/3/1。最大的问题是方向轴——读者以为拿到的是完整版，跑出来对不上，信任一次性破产。脱敏可以，但**必须声明脱敏**。

### 9.12 例十二：一个「Awesome 列表」类仓库

- **结果**：无。
- **技术**：无（列表本身无机制）。
- **代码**：无。
- **方向**：有收录标准。
- **四对齐结论**：列表类的四对齐收缩为一条：**收录标准是否可判定**。这条不过，列表就是个人书签。

### 9.13 例十三：一个模型权重发布页

- **结果**：有评测分数。
- **技术**：有架构与训练数据概况。
- **代码**：有推理脚本。
- **方向**：明确禁止用途与许可证。
- **四对齐结论**：5/4/4/5。这类文档的四对齐通常做得最好——因为发布方知道「跑不起来就没人用」。

### 9.14 例十四：本仓这份长文自己

- **结果**：字数 ≥10000，可用脚本计数验证。
- **技术**：四轴定义 + 评分卡 + 十四例 + 六联想 + 引用清单。
- **代码**：`python gate/feynman_align_check.py` 可校验结构。
- **方向**：明确写出「本机制自己会怎么坏」（见第 12 节）。
- **四对齐结论**：**文档也要接受自己的尺子**。这是本节的最后一个例子，也是唯一一个可以被当场验证的例子。

## 10. 六条联想：把四对齐接到更老的智慧上

四对齐不是新发明，它只是把一些老道理装进了一个可打分的壳。以下六条联想，每条都说明「借了什么、不借什么」。

### 10.1 切斯特顿的篱笆（Chesterton's Fence）

> 「看到一道篱笆，如果你不知道它为什么在那里，不要拆。」

**借用**：删减导读时，先搞清楚每句话在防什么。很多「冗余」的段落其实在防一个具体的误解。
**不借**：不借它来为「历史包袱」辩护。篱笆若真有理由，理由要能说出来；说不出理由的篱笆，该拆。

### 10.2 海勒姆定律（Hyrum's Law）

> 「只要有足够多的用户，你 API 的所有可观察行为都会被依赖，不管你在文档里承诺了什么。」

**借用**：文档的「承诺」永远小于「实际可观察行为」。所以四对齐要求把「失效条件」写出来——那是唯一能提前告知「可观察行为」的地方。
**不借**：不借它放弃文档。恰恰相反，正因如此，文档要写「什么会变、什么不会变」。

### 10.3 古德哈特定律（Goodhart's Law, 1975）

> 「当一个指标成为目标，它就不再是一个好指标。」

**借用**：四对齐一旦变成「凑满四节」，就会立刻退化。所以评分卡要求写**扣分原因**，而不是只写分数。
**不借**：不借它否定量化。量化仍然必要，只是必须配「反形式主义」的检查。

### 10.4 林迪效应（Lindy Effect）

> 「对于不会自然消亡的事物，已存在的时间越长，预期剩余寿命越长。」

**借用**：导读里最耐用的部分，通常是「为什么」而不是「怎么用」——因为工具会变，问题不会。四对齐把技术轴的「为什么有效」放在显眼处，就是在押注林迪。
**不借**：不借它反对更新。林迪说的是「不要因为新就换」，不是「不要更新」。

### 10.5 波普尔的可证伪性（Popper, 1963）

> 「一个理论如果不能被任何观察反驳，它就不是经验科学。」

**借用**：这是「上热门保证」为什么不承诺 star 数的根本理由——不可证伪的承诺是宣传，可证伪的承诺才是契约。四对齐的每一条都设计成「可以被判不合格」。
**不借**：不借它走向「什么都不可信」的虚无。可证伪不等于不可信，只是要求证据。

**这条联想对本文自身也成立**：本文说「四对齐能让导读更难被误解」，这个主张可以被证伪——办法是找一个没读过本文的人，按本文的评分卡给同一份 README 打分，若两位评分者差距超过 1 分，说明评分卡本身不可操作。这个实验我们还没做，所以这句话的状态是「待验证」，不是「已证明」。**把未验证的话标成未验证，是四对齐最容易被自己违反的一条。**

### 10.6 孙子「多算胜」（《孙子兵法·始计篇》）

> 「夫未战而庙算胜者，得算多也；未战而庙算不胜者，得算少也。」

**借用**：发布前的四对齐就是「庙算」——不是算敌人（竞品），是算自己：结果有没有数、技术有没有理、代码能不能跑、方向有没有界。四算皆备再发，是成本最低的胜负手。
**不借**：不借它把发布当战争。开源不是零和，读者的 star 不是从别人那里抢来的。

## 12. 这套机制自己会怎么坏（四种失败模式）

任何机制都要写自己的失效条件，否则它就违反了自己的第二条。

### 12.1 形式主义：为了过闸而写

**表现**：四节标题齐全，内容空洞；数字台账里全是「待补」。
**成因**：检查器只能查结构，不能查诚意。
**对策**：评分卡强制写「扣分原因」；每季度随机抽一份文档做人工复核，复核结果公开。

### 12.2 字数通胀：把「长」当成「好」

**表现**：为了达到字数要求，反复重述同一观点。
**成因**：字数是最容易作弊的指标（本文自己就有 ≥10000 字的要求，天然有通胀压力）。
**对策**：本文主动声明——**字数下限是防「太短以至于没讲清」，不是质量标准**。判断标准是「每 500 字是否新增一个可验证的信息点」。这条写在这里，是因为机制必须能审判自己。

### 12.3 表格崇拜：用结构代替论证

**表现**：满页表格，每格三个词，看起来整齐，实际没有因果。
**成因**：表格给读者「已梳理」的错觉。
**对策**：表格必须有「为什么」列，或紧跟一段解释。没有解释的表格是排版，不是论证。

### 12.4 自证陷阱：自己给自己打分

**表现**：作者自评 4.7，读者实测 2.1。
**成因**：评分者和被评分者是同一个人。
**对策**：对外发布前至少一次**外部对拍**（让没写过这份文档的人按导读跑一遍，记录卡在哪一步）。本仓的做法是把「跑不通」当成 issue 的默认入口，并承诺 48 小时内回应。

## 13. 机器校验：把「写没写」变成闸门

### 13.1 为什么必须机器化

因为「应答式环节不进流程图必被惯性漏掉」。人会在赶时间时跳过自检，机器不会。所以四对齐的**结构部分**（有没有三问、有没有四轴、数字台账在不在）必须由脚本判定。

### 13.2 校验器做什么、不做什么

| 做 | 不做 |
|---|---|
| 检查 README 是否有费曼三问 | 判断三问写得好不好 |
| 检查四轴章节是否齐全 | 判断论证是否成立 |
| 检查数字台账是否存在 | 复跑台账里的每个数字（那是 proofs 的职责） |
| 检查命令是否可执行（存在性） | 判断命令输出是否符合预期（那是 exit code 的职责） |

**边界写清楚**：校验器保证「不缺件」，proofs 保证「数是真的」，人保证「话是通的」。三者不可互相替代——这也是四对齐的一部分。

### 13.3 用法

```
python gate/feynman_align_check.py --repo .
```

返回 0 = 结构齐全；返回 1 = 缺件（fail-closed，缺件时绝不返回 0）。

## 14. 与 Star 互推、「上热门保证」的关系

### 14.1 导读质量决定 star 转化率

star 不是被「求」来的，是被「读完第一屏后觉得值得存一份」换来的。四对齐做的正是第一屏：**一个可复跑的数字 + 一句和你有关的话 + 一条能立刻执行的命令**。

反过来，如果第一屏是「业界首个」，读者不会 star——因为他不知道存下来干什么。

### 14.2 互推的正确姿势

本仓与姊妹仓（`irep-video-acceptance-ci`）互相推荐，但**不做 star 交换**。理由：

1. star 交换是刷量，违反平台规则，也是自欺——它污染了唯一能反映真实需求的信号；
2. 互推的价值在「读者路径」：看完协议想知道「这东西能省钱吗」，就去分仓；看完分仓想知道「凭什么信这套尺子」，就回主仓。这是**内容互补**，不是**数字互换**。

### 14.3 「上热门保证」为什么不能保证 star

因为 star 数是平台算法的输出，不由作者控制。承诺自己控制不了的东西，是营销；承诺自己能控制的东西，是契约。本仓只承诺后者（见两份 README 的 Trending Pledge 段）。

## 16. 补充：六种边界情形（机制在真实团队里会遇到的岔路）

前面十五节回答「怎么对齐」。这一节回答「不好对齐的时候怎么办」——因为真实的仓库很少长成教科书的样子。

### 16.1 情形一：仓库合并（两个仓变一个）

合并时最容易发生的事，是两份导读各自完整、合起来矛盾。四对齐给出的处理顺序是：

1. **先对方向轴**。两个仓的「不做什么」是否冲突？如果一个是「不碰专有软件」、另一个是「专做专有软件互操作」，合并后方向轴必然自相矛盾，这类冲突无法用措辞掩盖，只能在合并前解决。
2. **再对代码轴**。两套命令是否有同名不同义？是否有环境变量互相覆盖？这类冲突会让读者在第一步就失败。
3. **然后对结果轴**。两套数字的口径是否可比？如果一个是「平均误差」、一个是「最大误差」，合并后的台账必须拆成两行，不能合并成一个更好看的数。
4. **最后对技术轴**。机制命名去重：同一个东西有两个名字，是合并后最常见的长期债务。

**判断标准**：合并后的导读，读者能否只用一份文档跑通全部命令。不能，就没合完。

### 16.2 情形二：项目迁移（换语言、换平台）

迁移时导读最常见的错误，是把旧导读原样保留，只在顶部加一句「注意：已迁移到 X」。

四对齐要求的是**重写第一屏，保留技术轴**。理由：第一屏讲的是「怎么用」，平台变了它就全错；而技术轴讲的是「为什么有效」，机制本身没变，这部分是最值钱的资产，必须原样继承并注明「此机制在新平台上仍是同一机制」。

这里有个具体判据：迁移后如果导读里的命令全都变了、但「失效条件」一字未改，说明作者只是在换壳；如果「失效条件」也跟着变了，说明他真做了迁移。

### 16.3 情形三：项目废弃（archive）

废弃仓库的导读应当承担一个特殊职责：**告诉后来者为什么废弃**。

四对齐在废弃场景下的最小要求只有两条：结果轴写「最后一版的能力边界」，方向轴写「不要再用它的三个理由 + 推荐替代」。技术轴可以保留（它是历史资料），代码轴可以标注「不再维护，命令可能失效」。

**反例**：直接 archive 而不改 README。后果是三年后仍有人 clone 下来踩坑，而那份 README 还在承诺「持续维护」。这是最廉价也最常见的失信。

### 16.4 情形四：多语言文档（本仓就是）

中英双份导读最大的风险不是翻译不准，是**两份内容不同步**——英文加了新数字，中文还是旧的。

对策有三层：
1. **结构对齐**：两份文档的章节标题一一映射，不能一边有「失效条件」另一边没有；
2. **数字同源**：所有数字只在一处定义（本仓是 proofs 的输出），两份文档都引用同一处，不各写一遍；
3. **主次声明**：明确哪一份是权威版本（本仓以英文 README 为权威，中文为镜像，镜像滞后以英文为准）。

「明确主次」比「追求绝对同步」更现实——因为绝对同步需要每次改动都双写，而人的记忆不可靠，工具的检查才是可靠的。

### 16.5 情形五：团队协作（多人写同一份导读）

多人协作时，四对齐会退化成「谁最后改谁说了算」。破解办法是把四轴变成**评审清单**，而不是写作建议：

| 评审项 | 谁来判 | 判不过怎么办 |
|---|---|---|
| 结果轴：数字有无新增/改动 | 提 PR 的人自己举证 | 无出处不予合并 |
| 技术轴：机制描述是否仍在代码里成立 |  reviewer 对照代码 | 描述与代码不符，以代码为准并改文档 |
| 代码轴：命令是否仍 exit 0 | CI 跑 | 红了不许合 |
| 方向轴：负向声明是否被弱化 |  reviewer 专门看「删除行」 | 删除负向声明必须单独说明理由 |

最后一行是关键：**多数文档腐化不是从「新增错误」开始的，是从「删掉限制」开始的**。只审新增内容的评审流程，会系统性地漏掉这类腐化。

### 16.6 情形六：机器生成文档（AI 写的导读）

这是最近三年才普遍出现的情形，也是四对齐最需要提前设防的地方。

AI 生成的导读有三个特征：结构完整、措辞流畅、**证据稀薄**。它极易通过「结构检查」，这正是为什么第 13 节的校验器只能保证「不缺件」。

四对齐对此的补充规则是：**任何由机器起草的段落，必须由人对「结果轴」与「方向轴」逐条签字**。理由很直接——机器可以编出一个格式完美的数字台账，但它无法替你承担「这个数字是假的」的后果。

一个可操作的检验：随机挑导读里的三个数字，要求起草者当场指出「哪一行代码产出它」。指不出，就说明这段是生成的修辞，不是文档。

### 16.7 情形七：分叉与衍生仓（fork）

分叉之后，原仓与衍生仓的导读会迅速分道扬镳。四对齐对此的要求是**归属对齐**：衍生仓必须在首屏保留对上游的署名与链接，并写明「改了什么、没改什么」。

这不是礼貌问题，是可验证性问题：读者如果不知道哪些是上游的、哪些是衍生仓改的，就无法判断该信任哪一部分。归属一旦模糊，两份文档的可信度会一起下降——因为读者无法区分「上游的严谨」与「衍生的修饰」。

反过来，上游也有一条义务：如果衍生仓指出了错误，上游应在合理期限内回应并更正，否则「可被证伪」就只是姿态。本仓对此的承诺写在 README 的 Trending Pledge 段：任何被证伪的主张，七日内公开更正。
